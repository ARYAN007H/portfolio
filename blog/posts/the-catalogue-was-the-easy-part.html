The catalogue was the easy part

Twelve spec sheets, one static site, and the small lies we tell about launch week.

By Aryan 02 Nov 2026 5 min Filed under: design, the web

Twelve projects is a stupid number to put on one page. Not because twelve is a lot, but because each one wants a different sentence. A chess engine wants a number. A music player wants a feeling. A gallery app wants a screenshot and an apology for the build times.

The portfolio started as a PDF. Then it became a website that looked like a PDF, which is a different and much more stubborn thing. I wanted it to feel like a catalogue you could pull a card out of, not another dark hero section with a gradient and a "let's build together" button.

So every project got a sheet: a kicker, a spec table, a short argument for why it exists, screenshots, and — where a release exists — tear-off download slips. The whole thing is plain HTML and CSS. There is no build step, no framework, and no CMS. If the internet survives, the site should still open in ten years.

Half of it was remembering

I thought the hard part would be the design. It wasn't. The hard part was going back through twelve repos and working out what each one actually did, which screenshots were real, which releases still existed, and which README claims had quietly stopped being true.

That's the part nobody warns you about. A portfolio is an audit. You sit down to show your work and discover that three projects are half-finished, one has a broken install link, and the one you're proudest of has a screenshot from a version that no longer runs.

I fixed the links. I labelled the mocks. I deleted a sentence about a feature that never shipped. The catalogue got better because the catalogue made me check.

The barcode in the footer is CSS. It scans as nothing. I like it anyway. — print shop logic

Static, and stubborn about it

The site is static on purpose. The only moving part is a small script that asks the GitHub Releases API for version numbers and download links. When the API is slow or rate-limited, the HTML already contains a fallback. No spinner, no skeleton, no "something went wrong." The page works before the network answers.

Two small decisions I'd make again:

  • Self-hosted fonts. Fraunces, Space Mono, and Caveat, subset to Latin, served from the same folder. It keeps the type consistent and removes a third-party request from the critical path.
  • Cache-busting by hand. When the CSS changes, the version in the ?v= query changes. It is not elegant. It is one line and it always works.

The thing I didn't expect was how much the paper metaphor would constrain the writing. A spec sheet can't ramble. It has a column for language, stars, release, date. It forces you to say what the thing is before you say why it matters. I've started writing READMEs the same way.

A catalogue doesn't make the work better. It makes you honest about the work.

The receipt, not the work

"Price: Free" is in the masthead as a joke, but it's also the standing order. No accounts, no paywall, no tracking. The portfolio is the receipt for that promise: here are the things, here is what they cost you, here is where to get them. The design is loud because the offer is quiet.

I still think the catalogue was the easy part. Building twelve things took three years. Explaining them took a month. But the explaining is what turned a folder of repos into something I can hand to another person without saying "uh, start with the pinned ones."

If you're putting off a portfolio because the projects aren't ready: make the sheets anyway. The gaps are useful. They tell you what to finish.
